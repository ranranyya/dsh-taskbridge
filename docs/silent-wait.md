# 静默等待与集中审查（Silent waiting and concentrated host review）

本页说明 DSH Delegate `1.1.0` 引入、并由 `1.2.0` 修正的行为：一个正常推进的任务**不再**让
派工方（Codex）一遍遍醒来读结果；只有当出现真正需要判断的事情时，派工方才被打扰。

`1.2.0` 的修正集中在三处，读本页时请一并参照：等待被中断不等于执行被中断（第 4.1 节）、
串行宿主下的独立控制通道（第 4.2 节）、已安装 Codex 集成的自动升级（第 8 节）。

这不是"让 Codex 不花 token"的承诺。插件无法控制 Codex 自己的上下文、思考或工具调用
开销，也不做省 token 的估算。这里只描述**任务状态的报告方式**改变了什么。

---

## 1. 默认间隔

| 设置 | 默认 | 范围 | 含义 |
| --- | --- | --- | --- |
| `monitoring.selfCheckSeconds` | 300 秒（5 分钟） | 30–3600 秒，整数 | 任务完全安静这么久之后，插件在本机做**一次**只读自检 |
| `monitoring.attentionSeconds` | 600 秒（10 分钟） | 31–7200 秒，整数，且必须大于自检间隔 | 仍然安静这么久之后，才把这件事报告给派工方 |
| `monitoring.repeatFailureThreshold` | 3 次 | 0–20，整数；`0` 表示关闭 | 同一工具、同一操作、同一失败**连续**这么多次时提醒**一次**（与上面两个间隔独立，见 4.3） |

保存在设置文档里的单位是**整秒**。设置页用"分钟"呈现，二者是同一个值
（5 分钟 = 300 秒）。一个不是整分钟的值（例如 90 秒）在页面上显示为 1.5 分钟，
不会被悄悄圆成别的设置。重复失败提醒是一个**次数**，不是时长。

这三个值都只能全局设置：项目覆盖和单任务覆盖都**不能**改动它们，且每个任务在提交时冻结
自己那份有效值——运行中修改只影响之后新提交的任务。没有这个字段的旧设置文档照常加载，
按默认 3 次处理。

## 2. 核心规则：安静 ≠ 失败

- 任务安静、某个测试跑得久、某个工具调用耗时很长，**都不会**让插件判定失败、
  取消任务或重启任务。
- 真正推进（模型输出、推理、工具调用、工具结果）会**重置**静默计时，属于内部事实，
  不会叫醒派工方。
- 只有"确实没有进展"**并且**超过提醒间隔之后，才会报告 `attention`。
- 提醒只是提问，不是判决。派工方默认应当继续等待同一个任务，除非有**具体**的错误。

连接心跳、结果轮询、页面刷新这类噪声**不会**重置静默计时；否则一个真的卡住的执行器
会永远看起来"很活跃"。

## 3. 5 分钟自检做了什么、没做什么

达到 `selfCheckSeconds` 时，插件对**自己已经持有的**任务记录做一次只读检查：

- 任务是否还活着、执行器是否已经结束；
- 当前阶段；
- 是否有一次工具调用在等待授权决定；
- 当前正在运行哪个工具、已经运行多久。

它**不会**：

- 调用任何大模型（不消耗 token）；
- 读取或分析整个代码差异、也不会读工作区文件内容；
- 改变任务状态、延长或缩短任务的时限；
- 重启、取消或重新提交任务。

自检的结论会显示在任务详情里（"无进展诊断"），例如"执行器健在，这段时间没有新输出"、
"某个工具调用仍在运行"、"正在等待本次调用授权决定"。

## 4. 一次等待只返回一个结论

派工方通过 `delegate_wait({ taskId })` 等待同一个任务——**不传 `waitSeconds`**。一次调用的默认截止是
**3600 秒（60 分钟）**，内部由若干次**各自不超过 25 秒**的有界观察组成（执行面自己的上限也是 25 秒）；
正常的任务在内部大约每 25 秒完成一次观察，安静的 20 分钟就是 48 次观察、47 次心跳，而派工方
**只收到 1 个答案**。

这个 25 秒的内部节奏**属于程序自身**，不是派工方模型的轮询频率：它不要求、也不暗示派工方每个
周期做任何事。正常等待期间派工方应当保持安静——不读中间代码或 diff、不做并行实现或调研、
不复述没有变化的快照；审查集中在交付时做（见第 6 节）。

答案里是一个原因：

| 原因 | 含义 | 派工方该做什么 |
| --- | --- | --- |
| `heartbeat` | 没什么要报告的（内部心跳） | 正常情况下看不到；看到了就继续等待同一任务 |
| `attention` | 任务**整整**超过提醒间隔没有任何进展（默认 10 分钟）；**不是**"等待结束"。也可能代表**重复失败**（见 4.3） | 读诊断，**默认继续等待**；不要在只是安静时取消或判失败 |
| `permission` | 有一次工具调用在等授权决定 | 审查这一次调用的完整操作，然后决定一次，再继续等待同一任务 |
| `ready` | 执行结束，等待宿主审查 | 读**一次**完整证据，自己审查；这不等于已接受 |
| `failed` / `cancelled` | 运行没有产出 | 读一次记录的原因后报告 |
| `interrupted` | **任务记录本身**已中断（例如进程重启留下），不会继续 | 读一次记录后报告；不要继续盲等同一任务 |
| `wait-limit` | 本轮等待预算用完，任务没有任何变化 | `actionable: false`、`terminal: false`：不需要任何业务判断，立刻用同一 `taskId` 再等（不传 `waitSeconds`） |

**`actionable` 的含义**：只有真正需要派工方处理的原因（`attention`、`permission`、`ready`、
`failed`、`cancelled`、`interrupted`）才是 `actionable: true`。`wait-limit` 是 `actionable: false`：
它只说明**这次调用**自己的预算用完了，不是任务事实，也不需要决定。这个标志描述的是答案本身，
**不承诺**派工方宿主不会因此唤醒它自己的模型——是否被唤醒由宿主管。

`attention` 提醒有冷却：同一次静默里，第一次到达提醒间隔时报告一次；之后要再经过一个
提醒间隔才会再报一次。真实推进会让计时重新开始。

### 4.0 外层续等：宿主提前交回调用时

插件拥有的是 **MCP 等待**；它**不拥有**派工方宿主的调度（例如 Codex 的 exec/tool 时限）。
插件默认等 3600 秒、托管条目的 `tool_timeout_sec` 是 3660 秒，这两件事都已存在，但宿主仍可能
用**自己的**限制提前把调用交回。这是**外层**事件，合同如下：

- 外层交回**不等于** MCP 等待结束，也不是 `wait-limit`：那两个只有答案自己的 `reason` 字段能报告。
- 它不说明任务停止，也不说明任务完成——执行可能完全照旧在进行。
- 已有 exec cell 还在跑，就**续接同一个 cell**；不要重开一次 `delegate_wait`、不要读
  `delegate_result`、不要轮询 `delegate_status`、也不要提交重复任务。已经拿到的 `taskId` 就是
  需要的全部状态。
- 选择**客户端实际支持的最长 yield**。客户端提供 yield/pragmas 参数时，正常等待应该请求**约
  1200000 毫秒（20 分钟）**这个量级，而不是一分钟；按习惯 1 秒/几秒续等不是等待，而是换了外壳的
  轮询。
- **一分钟不是固有限制**，那只是调用者的选择；不要把它写成客户端的上限，也不要声称每个客户端都
  支持同样的长 yield——只说明这个客户端实际接受什么。
- 把控制权交回给操作者是 **UI 决定**，不是"委托观察已停止"的声明。插件自己的观察循环继续，
  worker 继续运行。
- **能力边界（必须诚实说明）**：插件不能在你的宿主里创建后台等待进程、定时器或回调来"自动唤醒"
  你。若可用的 yield 确实很短、又没有自动续接，那么一次长等待确实要占用"每个 yield 窗口一次恢复
  回合"。这种情况应当**如实告诉操作者一次**；不要虚构后台唤醒，不要声称插件会在后台通知你，也不要
  去改操作者的 Codex 配置绕过它。

### 4.3 重复失败提醒（与静默计时独立）

除了两个静默间隔，插件还会盯着**同一个工具、同一个操作、同一种失败连续出现的次数**。两者互相
独立：一个忙碌的任务可以一直在失败，永远碰不到 5/10 分钟阈值，而这正是这个提醒存在的场景。

- 默认连续 **3** 次时提醒**一次**；设置项 `monitoring.repeatFailureThreshold`，`0` 表示关闭。
- 只认**原生结构化失败标记**：`tool/result.message.isError === true`（`ToolResultMessage` 契约）。
  输出里出现 "error" 字样、任务安静、只有思考、测试跑得久、或者没有改文件，都**不是**失败。
- 同一个 `callId` 的重复结果只算一次；工具、操作或失败码**不同**，或者中间出现一次成功，
  都会结束/切换当前 episode。一个 episode 只**生成**一条提醒（到达阈值的那一刻），这条提醒
  在被确认前会以同一身份**重放**；被确认（或因恢复/切换而失效）后才安静，之后新的 episode
  可以再生成一条新提醒。
- 它沿用 `attention` 这个 reason，并额外携带 **`failure`** 块：
  `{ kind: "repeated-tool-failure", eventId, toolName, failureCode, consecutive, threshold, ... }`。
  这是**有类型**的紧凑诊断，不是文本猜测。`eventId` 是这条提醒的稳定身份（16 位十六进制，
  每个任务的 monitor 有独立的随机命名空间），不含任何参数或错误正文。
- **重放直到确认**（TB-09/TB-10）：提醒不是"取走即清空"。observe 的 HTTP 回答丢失后，
  客户端重试会得到**同一个** `eventId` 的同一条提醒；同轮后续失败也不会生成新的提醒身份。
  服务端已生成响应（甚至已写出）都不等于接收方已收到，只有接收方凭 `eventId` 的显式确认
  才停止重放：宿主在下次 `delegate_wait`（或直接 observe）携带 `ackFailureEventId`，答案的
  `failureAck` 字段回报确认事实。`acknowledged: true` 才是已确认；`false` 时按 `reason`
  区分：`unknown-event`（错误/未知 id，不得盲重试，继续同任务等待并处理新事件）、
  `superseded`（旧 episode 已被取代，无需再确认）、`no-pending`（任务已终结）、
  `event-id-required`（确认字段为空）。确认成功后的等待即使随后报错或被取消，答案（或拒绝）
  中仍保留已确认事实，不会把不确定说成成功。
- 未确认提醒会随每次 observe 以同一身份重放，因此**旧客户端（不发确认）的明确行为**是：
  同一条提醒会重复出现，直到该 episode 结束或被确认——这是回包丢失可恢复的必要语义；
  新宿主按 `taskId` + `eventId` 去重，并在下次等待时确认。
- 它只提醒，**不自动**取消任务、更换模型或改变超时。授权请求和终态**优先**于它。
- 只保留散列与计数：操作的 sha256 前缀、失败码、次数、时间；不保留也不发送原始参数、思考、
  输出或密钥。终态后释放，只留一段有界证据。

### 4.1 等待被中断 ≠ 执行被中断

引擎会在**观察者自己的这次请求结束**时报告 `interrupted`（调用方取消、连接断开、引擎在
重建时释放了等待者）。这时任务仍在运行。所以：

- `state` 是 `pending`/`running` 且 `endedAt` 为 `null` 时，这次中断只代表本次观察结束：
  答案立刻返回 `reason: "interrupted"`、`terminal: false`、真实任务状态，指令要求继续等同一
  `taskId`。一次调用**不会**在内部重发观察：被释放的观察者会让每次观察都立刻返回
  `interrupted`，重发就成了请求风暴。
- 只有任务记录本身是 `state: "interrupted"`（重启历史）才是不可恢复的终态：
  `terminal: true`，并且指令明确要求停止盲等、读 `delegate_result`。
- 中断同时带着真实结局时按结局返回：`awaiting-host-review` → `ready`，`failed` → `failed`，
  `cancelled` → `cancelled`，所以已完成的运行照样进审查。
- 状态缺失或未知（本构建不认识的状态字符串）时不做断言：`terminal: false`，指令要求先核对；
  既不宣称"已停止"，也不宣称"仍在运行"。
- `metrics.interruptedObservations` 单独计数，不和心跳混在一起。

任务记录页把真实的 `interrupted` 历史显示为「已中断（进程重启后不会继续执行）」，不会显示
成"仍在运行"。

## 4.2 串行宿主：独立控制通道

插件自己的 stdio MCP 服务器本来就**支持并发**：一个长等待在飞时，status、cancel 照样能被
回答。瓶颈在外层宿主——一次只转发一个工具调用的客户端会让整条连接被等待占住。

插件**不承诺**改变宿主的调度器，也不把长等待退化成轮询。可用的是独立本地控制程序：

```bash
node bin/dsh-delegate-control.js status <taskId>   # 紧凑 JSON 状态（observe + 最小有界观察）
node bin/dsh-delegate-control.js cancel <taskId>   # 只停止这一个任务
```

- 与 MCP 服务器使用**同一个** `createExecutionClient` 与端点发现，调用现有 loopback 执行面；
  不新增权限、开关、配置接口，也没有常驻后台进程。
- 只有这两个动作：没有提交、设置、总开关、批量取消或默认放行。
- `status` 请求的是**最小有界观察**（`waitMs: 1`，引擎与监控都保留的最小正数），不是
  `waitMs: 0`。`0` 在这两处都被理解成"调用方没指定上界"，会被替换成 25 秒的默认长等待，
  反而让一次状态查询超出这条命令自己的预算。它仍然只回答**当前状态**：已结束的任务和待授权
  请求在任何定时器启动前就返回，仍在运行的任务只观察一个切片；永远不读完整结果、diff 或对话。
- **整次命令只有一份总预算**：默认 **10 秒**，`DSH_DELEGATE_CONTROL_TIMEOUT_MS` 只能把它**调小**
  （填更大的值会被夹回 10 秒；缺省或不可用的 `timeoutMs` 也按 10 秒算）。这份预算通过调用方的
  `AbortSignal` 生效，同时**对本次调用禁用观察重试**——否则 1 秒/2 秒/5 秒的退避会超出预算，
  或者在命令已经回答之后还留着请求在跑。没有 `Promise.race`，也不留后台请求或进程。
- 任何断线、超时都变成有界 JSON + 非零退出码（预算耗尽是 `CONTROL_TIMEOUT`），没有堆栈、没有秘密；
  退出码 `0` 有答案、`1` 被拒绝或超时、`2` 用法错误。
- 普通等待**不会周期性跑 status**：这个通道只在操作者或用例显式调用时才发起请求。
- 等待监听断开只释放观察，**取消永远是显式 `cancel`**。
- 工具目录补上了准确的 MCP `annotations`（例如 `readOnlyHint`），便于支持并发的客户端识别
  长等待是只读调用。注解不是修复，串行客户端照样忽略它。

## 5. 等待授权不是卡住

任务等待一次工具调用的授权决定时，仍然是 `running`，阶段是 `awaiting-permission`。
它保留工作区锁和并发名额，并且：

- 这一段等待**不计入**执行超时（有单独的、固定的请求截止时间）；
- 不会被报告成"长时间没进展"；
- 授权决定只对**那一次调用**有效，不构成常规权限，也不会被后续调用复用。

### 5.1 决定之后直接续等（`waitAfterDecision`）

`delegate_permission_decide` 有一个可选参数 `waitAfterDecision: boolean`，默认 `false`。

- **省略或 `false`**：行为与之前完全一致——只做决定，返回权限路由自己的原样答复
  （`ok`/`task`/`permission`/`hostAcceptance`），不额外增加任何字段。旧客户端不受影响。
- **`true`**：在同一次 MCP 调用内，决定被后端确认生效后，**复用同一个等待循环**
  （`delegate_wait` 的那一套：25 秒一次的受限观察、默认一小时的截止时间、心跳处理、
  `interrupted` 分类）继续等同一个 `taskId`，直到出现真正需要判断的事件。

答复形状是**扁平的 `delegate_wait` 形状 + `decisionReceipt`**：`reason`/`state`/
`actionable`/`terminal`/`permission`/`task` 在顶层，新申请仍带完整的脱敏操作、
`completeness` 与 `fingerprint`。不嵌套 `followUpWait` 这样的子块，因此已有的
`boundedJson` 权限保护照旧生效：答复过大时，**回执和当前待定申请都会保留**，
被截短的操作会明确标记为不可放行（`permissionDecidable: false`），不会被当成完整操作。

`decisionReceipt` 说明决定本身的结果，例如
`{ taskId, requestId, decision, fingerprint, applied, confirmation, outcome?, verified? }`：

| 情形 | 回执 | 含义 |
| --- | --- | --- |
| 后端确认生效 | `applied: true`、`confirmation: "applied"` | 决定已生效，后续等待失败或取消都不会撤销它 |
| 后端明确拒绝 | 抛出原有拒绝码，无回执 | 决定未生效，也不会有任何等待开始 |
| 传输失败、超时、畸形答复 | `applied: null`、`confirmation: "unknown"` | **不知道**是否已生效；先读任务真实状态，不要直接重送 |
| 答复与所决定的不一致 | `applied: null`、`confirmation: "unknown"`，附 `reason`/`evidence` | 答复中的 task、request 或 operation 与实际不符，或缺少 `state`/`outcome` 等必要证据 |
| 答复 `ok: false` 或缺证据 | 同上 | `applied` 只可能来自**匹配的真实证据**，不会因为"有答复"就置真 |
| 答复过大被裁剪 | 最小回执：身份 + `applied` + `confirmation`（`evidenceOmitted: true`） | 大块 `grant`/`verified` 证据被丢弃并可另读，但回执身份不丢 |

确认"已生效"要求同时满足：`ok: true`、同一 task、同一 request、同一 operation fingerprint、
`state` 为已结算、`outcome` 与本次决定一致（`allow-once` 对应 `allowed-once`，
`reject` 对应 `rejected`）。`allow-once` 还需要 `verified` 证据，`reject` 不需要。
真实后端记录的 `decision` 字段可能为 `null`，因此不把它当作必要条件；判定依据是
`outcome` 与实际证据。**引用的 fingerprint 不会被后端值静默替换**：不一致就是矛盾。

几条固定规则：

- **已经决定的申请不会被再次询问**：等待循环按 `requestId` + `fingerprint` 完整匹配跳过
  旧记录；**新 `requestId`，或同一 id 但操作变了，都是新问题**，不会继承上一次的允许。
- **决定被拒绝时不会进入等待**；决定是本次调用的第一次请求，所以被拒时不会留下任何观察。
- **决定已生效而后续等待失败/被取消/抛错时，本次仍是成功答复**：`decisionReceipt.applied`
  保持 `true`，`reason` 为 `null`（没有观察到任何任务状态，就不编造），并附
  `waitError`（含 `phase: "follow-up-wait"`）与"不要重送决定、执行未被停止"的明确指引。
  回执只保证在**真实已生效**这一分支不丢；它不意味着任何答复都能恢复任意失败的决定。
- **无法确认的决定不会进入等待**：拒绝码为 `MCP_DECISION_UNCONFIRMED`（或传输失败时保留
  后端码），`error.details.decisionReceipt` 带 `applied: null` 与原始身份。
- 同一请求重复提交仍由现有引擎拒绝；恢复时先读真实状态，不伪造幂等批准。

## 5.2 计量（`delegate_metrics`）

`delegate_metrics` 是**本 MCP 进程**的只读计数，不需要任务 id：

- 每个工具被调用了多少次；每次等待返回的原因、耗时、内部观察次数；
- 交给宿主的**工具文本字节数**——在最终脱敏、裁剪后的文本上，用
  `Buffer.byteLength(..., 'utf8')` 计量，不是字符数，也不是答复里自报的自身长度。
  它表示"交给传输层的数据量"，**不等于**宿主确认收到；
- 已生效的决定次数，以及每次决定之后那次等待的关联 id。

它**不**记录工具参数、思考正文、答复正文、密钥或任务内容。宿主模型自己的轮次、
token 用量和费用在这个进程里**不可见**，因此报告为 `not-integrated`，而不是填 `0`。
这里的数字是**程序**等待了多少，不是"叫醒了模型多少次"，本插件也没有任何
跨客户端的零唤醒承诺。

## 6. 集中审查：什么时候读证据

插件不会把对话内容、推理过程或工具输出塞进状态报告。派工方在**执行结束之后**
读一次完整证据（`delegate_result`），然后自己审查：

- 执行完成 ≠ 被接受。插件永远不自行验收；`selfApproved` 恒为 `false`，
  `hostAcceptance` 由宿主自己记录。
- 大改动只挑相关的文件各看一次，不要反复重读同一份证据。
- 派工期间只做等待：正常执行（`delegate_wait`）之外不读中间代码、不代为运行测试，
  也不用一次授权把实现接过来。Codex 负责规划、审批与终审，worker 负责实现。
  普通单个测试失败由 worker 自检修复，不自动触发指挥官诊断；只有确定阻塞、
  `attention`、真正异常或用户要求时，才做一次**有界**诊断，先事实后决定，仍不接管写实现。

### 审批核验的是操作本身

审批只核验**完整、具体**的命令或脚本、它涉及的每一条路径，以及进程归属（会运行谁的
程序、在哪个目录工作）。worker 给出的理由只是**待核实的声明**，不是证据也不是授权。

- 读源码不需要审批。简单的源码检索／字段查找用 PowerShell 内建
  （`Select-String` / `Get-Content`）；**不要**为了读一个文件去启动 `node` 或 Electron。
- 外部程序只有在**同一环境确有失败证据**时才值得单次申请，且只申请一条具体命令，
  并说明它解决哪个错误。
- 测试写到自己临时目录里的 fixture 提交**不等于**对源码仓库提交：不要因此拒绝，
  也不要把它当成改写历史。禁止的是在仓库里自行 commit / push / tag / 改历史。

1.4.0 增加 `delegate_review({ taskId, decision, note })`。派工方实际审查后记录
`accepted`（审查通过）或 `changes-requested`（需要修正），并填写简短事实或修改意见。
必须确认写回成功，才向用户说已记录。该动作不放行工具、不合并代码，不改变执行状态或路由；
任务页依据单独的审查记录显示结论。旧记录不自动通过，修正通过原任务续接产生新一轮交付。

## 7. 续接（跟进任务）

### 1.4.1：审查保存与长备注

原身份可读取和补审已结束的历史任务，重启不恢复执行或旧审批。审查备注统一最多
8000 Unicode 码点（输入去除首尾空白并脱敏），合法正文完整保存，超限或容量不足明确拒绝。
`reviewPersistence` 区分 `saving`、`timed-out`、`saved`、`failed`；超过 5 秒只是尚未确认，
不能宣称保存失败或提前通过。晚到结果通过状态读取确认；确定失败可重试。

等待仅带结论状态和长度。结果中的 `noteOmitted: true` 表示正文被明确省略，使用
`delegate_result({ taskId, reviewNoteOffset: 0 })` 按 `nextOffset` 读取；默认每页 2000 码点，
可选 `reviewNoteLimit` 范围 1—2000，直到 `complete: true`。列表 200 码点预览与详情展开
不改变保存正文；可见页面的待审／保存中刷新由程序完成，不唤醒 GPT。

### 同一任务继续修正

同一个任务的修改、纠正或重试，用 `continueFromTaskId` 提交，并继续使用**同一个**
已授权的源工作区路径。这样跟进任务会续接同一条 DSH 对话、落在同一棵工作树里。
不相关的任务不要复用 id，也不要为了"保持上下文"而续接。

**预检按任务链算，不按每次派工算。** 新任务照旧：`delegate_status` +
`delegate_preflight`（原始授权源路径）+ 脏树隔离决策。已经验证过的链条继续修正时，
只要源路径未变、任务目标与边界未变、且没有身份／隔离异常，就**复用已核验的预检事实**，
不再因为 worker 上一轮留下的候选改动而重做一次脏树决策——那些改动正是这个链条的预期状态。
需要重新核实时：源路径变了、任务不相关、出现身份／隔离拒绝、或引擎报告不一致。

复用预检**不改变**引擎的任何校验：每次提交仍然带**原始源 `workspacePath`** 与
**最新的 `continueFromTaskId`**，引擎每次都重新校验所有权、路径、原 checkout 与会话。
**绝不**用"改成新任务"绕过一次拒绝。

### 团队模式（Agent Teams）由指挥官按任务决定

`delegate_submit` 的可选布尔 `agentTeams` 选择 DSH 的 Agent Teams 模式
（模型菜单里的"启用智能体团队协作"）用于**本任务自己的** DSH 会话。它不是 Codex 自己的
多智能体功能，也不是附加审查模型。用户在派工制度上决定一次"由 Codex 按复杂度决定"，
不需要每次派工都问用户。

- 简单单文件或强顺序依赖的活：**显式**传 `agentTeams: false`（schema 支持该字段时）。
  **省略字段不等于关闭**——省略表示"没有做出新决定"，运行会保留（续接时继承）会话原有的选择。
  仓库 AGENTS 禁止再委派的场景必须显式 `false`，并交代哪些操作改由 root 执行（那些仍需正常审批）。
- 只有确实能拆成**可并行**的独立模块、且收益覆盖协调成本时才打开，并在派工文本里写明理由。
- 续接不重复决策：插件继承链条的选择，省略即沿用父任务；要让这一次跟进关闭，必须显式 `false`；
  只有范围变化足以推翻时才显式给出新值。
- 执行用的 provider / model / effort 仍由用户的配置决定，`agentTeams` **从不覆盖**它们。
- 只通过这个 schema 字段表达。工具版本不支持时要**说明并请求加载新集成**，
  不得伪造成功，也不得改用别的字段、任务文本或其他通道。
- 团队成员按 DSH 原生策略运行（子成员的审批默认 `never`），只能在既有范围内工作；
  需要额外权限的**具体动作由 root 执行**，再走本通道原有的单次审批。
  不要宣称子成员审批已打通，不要放松 `owns`，不要改宿主策略。

### 审查证据的读法

`ready` 之后对同一任务只调**一次** `delegate_result`，按顺序读：
① 短摘要、改动文件清单、测试结果与日志路径、限制；② 只有审查缺口真正需要的文件，
一次一个文件或一个限定范围。**不要**整份倾倒大文件或全仓 diff——被截断就得重读，等于没读到。
把已核验的结论**连同证据路径**（文件+行号，或日志路径）记下来，后来的疑问用它回答。
审查结论**必须**通过 `delegate_review` 写回并确认 `saved`/durable；
只写一份报告不算审查记录。发现问题**集中一轮**成一份修正清单，续接原任务。

## 8. 已有用户如何升级

1. 在 DSH 的插件设置页打开 **Codex 集成**；
2. 点 **安装 / 更新 Codex 集成**（按钮会把这个插件发布的旧版本文件更新到当前版本）；
3. 让 Codex 重新载入：新开会话或重启 Codex。

`1.2.0` 起，**入口脚本路径未变的已安装托管条目不再需要手工点按钮**：插件启动自检会检查已安装的
`mcp_servers.dsh-delegate` 条目，只要它带托管标记、command 是本包的 Node 命令、`args[0]`
**正好是本安装的** `dsh-delegate-mcp.js`，而且**已经过期**（缺少 `tool_timeout_sec`），就在原地补齐。
入口脚本路径已经指向插件旧目录的条目，启动自检只会报告 `conflict`，不会替操作者改路径：请点
**安装 / 更新 Codex 集成** 或 **修复**，显式动作才会在证明该旧路径是同一包的**真实安装**
（真实目录 + `package.json` 的 `name` 与 `bin["dsh-delegate-mcp"]` 映射都对得上）之后采纳它。

更新会为托管 MCP 条目补上 `tool_timeout_sec = 3660`。客户端可能不认这个字段，或用自己的默认
工具超时提前结束等待（Codex 的历史默认是一分钟）；3660 秒只是把托管条目请求的允许时长设为
默认 3600 秒等待加一分钟余量，**不能**解除客户端自身的限制。这个字段只写在
**本插件自己的** `[mcp_servers.dsh-delegate]` 条目上：

- 旧版本写的、带托管标记的条目会被就地补齐，文件里其它内容原样保留；
- 没有托管标记的同名条目视为**你自己写的**，不会被改写、覆盖或删除；
- 值不是整数的条目同样视为别人的定义；
- 你自己编辑过的子智能体文件会被报告为"不属于已知版本"，插件不会改动它；
- 启动自检**不会创建**条目：没安装就什么都不写；
- `$CODEX_HOME` 或 `agents/` 是链接（含 Windows junction）时一律拒绝，连条目状态都不再
  穿过链接去读；
- 写前重新读取并重新判定，期间发生变化（漂移）就拒绝，不覆盖。

## 9. 已知限制

- 插件的监控只在**有人观察**时运行：没有派工方在等待时，它不启动定时器，也不消耗任何东西。
- 提醒阈值是安全网，不是进度条。插件**不**计算完成百分比，也**不**猜测还剩多久。
- 一次 `delegate_wait` 的默认等待是 3600 秒（上限也是 3600 秒），每次内部观察最多 25 秒；
  前者由工具本身约束，与 `tool_timeout_sec` 的关系是：后者必须比前者略大，才能让一整轮
  等待跑完。
- **客户端自己的工具超时不能证明任何事**：调用方宿主（例如 Codex 自己的工具时限）提前结束一次
  等待时，既不能说明执行已停止，也不能说明它还活着。保留 `taskId`，需要时读一次紧凑事实
  （`delegate_result`），然后继续等待同一任务；不要因为一次客户端超时就重复提交、重启或取消任务。
  等待被中断（`interrupted`）与客户端超时都不改变执行本身。
- 等待被中断不等于执行被中断；`interrupted` / `wait-limit` 的 `actionable`、`terminal` 与 `state`
  字段是判断依据，不要只看原因名字。
- 串行宿主下没有通用的“并发”承诺：插件传输支持并发，独立控制程序只提供 `status` 与
  `cancel` 两个动作，也不能改变宿主的调度方式。
- **四类"结束"不是一回事**，不要混用：(a) `wait-limit` 是**这次调用自己**的等待预算用完，
  任务本身没变，继续等同一个 `taskId`；(b) 外层宿主工具/执行时限把调用提前交回，是
  **外层事件**，观察没结束、执行也没停；(c) `attention` 是**真的没有活动**超过阈值
  （默认 10 分钟）；(d) 任务的**总执行超时**是执行方自己的预算，以终态报告，既不是
  `wait-limit` 也不是 `attention`，更不是客户端事件。
- 插件**不能**创建后台等待者、不能唤醒宿主模型，也**不**承诺跨客户端的零唤醒。宿主有
  自动续接时，一次长等待只占一个续接窗口；没有时，每个 yield 窗口要花一次续接。这一点
  必须如实说明，不能编造后台唤醒。
- 2026-11-14 的候选验收使用真实 Codex 外层调用、独立 stdio MCP 进程、本机 HTTP 通道与生产活动监控器，
  持续等待 1200 秒：内部观察 48 次、消化心跳 47 次，仅返回 1 次交付事件，期间没有读取中间结果。
  活动由脚本按真实事件格式模拟，包含持续思考流；这证明该客户端能够维持这次 20 分钟等待，
  **不等于**真实提供方连续执行 20 分钟、所有客户端零续接或固定比例的 token／费用节省。
- 设置页的自动刷新只在"任务记录"标签页可见、且存在进行中的任务时运行；
  终端状态的任务不会触发刷新。

## 1.5.0：原生提问、拒绝理由与真实验收

- 原生 `ask_user_question` 通过 `reason: question` 即时返回，问题处于 `awaiting-question`，不等十分钟停滞提醒。`delegate_question_answer` 回答一次；使用 `waitAfterAnswer: true` 可在同次调用继续等待原任务。
- 问题与选项完整传送；超过整体界限或含必须脱敏的内容时明确拒绝。若返回 `questionsOmitted: true` 或 `questionAnswerable: false`，不得依据残缺内容作答。
- `answerReceipt` 和 `decisionReceipt` 的身份、`applied`、`confirmation` 在结果裁剪或后续等待失败时仍保留。大批答案可标明省略，不反复回传全文；收到已应用回执后不要重送。
- 题目默认十分钟到期，最多三十分钟；DSH 原生调用若更早撤销，也立即失效。题目绑定同一 Agent、Session 和原工具调用，不会移交给新回合的同名调用。
- 审批拒绝理由注入同一个执行 Agent。`rejectionFeedback.delivered` 表示注入是否成功，不等于模型已理解；原操作仍被拒绝，后续申请独立判断。问题回答始终不授予任何权限。

2026-11-15，本地 test.2 候选通过实际 DSH Desktop 重启续接，以及真实模型12轮串行100秒工具等待/只读校验，整轮约21分23秒。1次 MCP 等待、1次ready返回、0次中间结果读取；外层客户端20分钟时仍需续接同一个exec。账单实测见[1.5.0等待阶段对照](releases/1.5.0-token-benchmark.zh.md)，不承诺跨客户端零唤醒或所有任务固定节省率。
